# Texture-file loader candidate at `0x8003CCE8`

The candidate recovers filename construction, file opening and loading, the
24-byte reader state, allocation of 12-byte GPU texture records, iteration
through `func_8003CB80`, page/palette selection, four UV corners, and release
of the loaded file. It is research-only and is not in the matching manifest.

The target frame is 256 bytes: the texture descriptor is at `sp + 0x10`, the
64-byte path at `sp + 0x38`, the 72-byte file handle at `sp + 0x78`, and the
reader at `sp + 0xC0`. Reader fields hold the cursor, entry count, current output,
output base, input base, and magic, in that order. The candidate reproduces
these stack locations and the saved-register set.

The current candidate emits 464 bytes for a 500-byte retail extent and differs
in 94 of 125 words, counting missing tail words as differences. The initial
path and file-loading calls match. Remaining differences include repeated
reader accesses through `t0` in retail, retention and reloading of stack reader
fields, the UV endpoint pointer in `s7`, and register allocation for the page,
palette, and corner calculations. Retail stores the first page through the
reader's current pointer, reloaded after page selection; the candidate instead
caches the output pointer across that call.

For a local compile, use the production unit's address, extent, and default
flags, and resolve every address-suffixed external name in the candidate to
its corresponding address. Do not give this candidate semantic coverage credit
until the full 500-byte comparison passes.
